# Roomark Android 软装读取失败保护设计

日期：2026-08-03

## 背景

Roomark 会在 Android 启动后预读取每套房源的本地软装项目。正常情况下：

- 存储键不存在时创建该房间的空白项目；
- 存储内容损坏时恢复可用部分，并在软装页面显示恢复提示；
- 存储读取超过既定期限或直接失败时，当前实现同样创建空白项目。

第三种情况存在数据覆盖风险。读取超时不代表设备中没有软装记录；如果页面把临时空白项目作为可编辑项目打开，用户的第一次家具变更会触发自动保存，从而覆盖仍可能存在的旧布局。

本轮只修复现有软装读取与保存链路的可靠性，不增加账号、云同步、社区、知识库、合同分析、真实空间扫描或真实 AI 效果图。

## 目标

当软装项目的设备读取失败或超时时：

1. 不把临时空白项目写入 `projectsByRoomId`；
2. 不挂载可编辑 3D 场景；
3. 明确说明设备中的原布局尚未被覆盖；
4. 提供原位“重试读取”和“返回房源库”动作；
5. 重试成功后恢复现有软装工作流；
6. 不改变正常空记录、损坏记录恢复、保存队列或存储键。

## 非目标

- 不改变 `roomark:furnish-project:<roomId>` 存储键。
- 不改变 `FurnishProject` schema。
- 不给 AsyncStorage 写入增加超时。写入不可取消，超时后放行后续写入会产生旧写入迟到覆盖新数据的风险。
- 不自动清空、删除或覆盖读取失败的记录。
- 不新增后台同步、远程备份或导出功能。
- 不把模拟器验证表述为真机、商店或生产签名验收。

## 方案比较

### 方案 A：阻断编辑并允许原位重试（采用）

读取失败时 Store 保留房间级读取错误，不发布空白项目。软装页面显示阻断式恢复页，用户可以重试读取或返回房源库。

优点：

- 在无法确认旧数据是否存在时不允许覆盖；
- 错误归属到具体房间，不影响其他房源；
- 重试成功后沿用现有 3D 与自动保存链路；
- 不改变存储格式。

代价：

- 读取持续失败时该房间暂时不能进入软装编辑；
- 需要新增房间级读取错误状态和少量页面分支。

### 方案 B：自动重试后继续空白项目

读取失败后自动再读一次，仍失败则打开空白项目。

优点是用户操作少。缺点是现场等待时间不可预测，最终仍可能覆盖未读出的旧布局，并且用户无法判断空白状态是真正无记录还是设备读取故障。

### 方案 C：继续当前恢复提示

保留空白项目和非阻断提示。

改动最小，但没有消除数据覆盖风险，不满足成熟产品的数据保护要求。

## 数据模型

`FurnishProjectLoadResult` 增加可选字段：

```ts
readFailed?: boolean;
```

语义：

- 存储键不存在：`recovered: false`，不设置 `readFailed`；
- JSON 可解析但内容损坏：沿用 `recoverFurnishProject`，不设置 `readFailed`；
- JSON 无法解析：沿用损坏记录恢复，显示恢复提示，不设置 `readFailed`；
- AsyncStorage 读取拒绝或超时：`readFailed: true`，返回仅用于满足结果类型的空白项目，但 Store 不发布该项目。

Store 增加：

```ts
loadErrorsByRoomId: Partial<Record<string, string>>;
```

读取错误按 `roomId` 隔离。成功读取同一房间时只清除该房间错误；其他房间的错误保持不变。

## 存储边界

`loadFurnishProject` 将读取与解析拆成两个错误边界：

1. `runStorageRead` 的拒绝或超时属于设备读取失败，设置 `readFailed`；
2. `JSON.parse` 失败属于已读到但损坏的内容，交给现有恢复逻辑生成带警告的空白项目。

这样可以区分“设备暂时读不到”和“设备已返回损坏内容”，并只对前者阻断编辑。

## Store 状态流

### 首次读取失败

1. `loadingRoomIds[roomId] = true`；
2. 存储返回 `readFailed: true`；
3. Store 不更新 `projectsByRoomId[roomId]`；
4. Store 设置 `loadErrorsByRoomId[roomId]`；
5. Store 清除该房间旧的恢复提示；
6. `loadingRoomIds[roomId]` 在 `finally` 中清除。

### 重试读取成功

1. 页面再次调用现有 `loadProject(roomMesh)`；
2. Store 复用同一房间的在途请求去重；
3. 成功结果写入 `projectsByRoomId[roomId]`；
4. 只清除 `loadErrorsByRoomId[roomId]`；
5. 正常挂载 3D 场景。

### 多房间并发

A 房间读取失败时，不修改 B 房间的项目、加载状态、恢复提示或读取错误。B 房间成功也不能清除 A 的错误。

## 页面体验

`FurnishStudioScreen` 在常规 loading 分支之前检查当前房间的 `loadError`。

读取失败页包含：

- 标题：“软装记录暂时无法读取”；
- 说明：“设备中的原布局尚未被覆盖。请重试读取，或返回房源库稍后处理。”；
- 主动作：“重试读取”；
- 次动作：“返回房源库”。

重试期间：

- 主动作禁用；
- 文案变为“正在重新读取…”；
- 不挂载 `FurnishWebView`、家具抽屉或 Mock 概念图动作。

正常读取、空记录和损坏记录恢复页面保持现有布局与文案。

## 错误处理

- 读取失败提示是房间级阻断状态，与保存错误、3D renderer 错误相互独立。
- 保存错误仍使用 `saveErrorsByRoomId` 和原有重试保存。
- 损坏记录仍允许恢复后编辑，并通过 `recoveryWarningsByRoomId` 说明发生了恢复。
- 返回房源库不删除错误状态；再次进入该房间时页面仍阻断，直到读取成功。

## 测试策略

### 存储行为测试

- AsyncStorage 读取拒绝时返回 `readFailed: true`；
- 读取超时由同一拒绝路径转换为 `readFailed: true`；
- 存储键不存在时返回正常空白项目，不标记失败；
- JSON 无法解析时进入损坏恢复，不标记设备读取失败。

### Store 行为测试

- 房间 A 读取失败后不发布空白项目；
- A 的错误不影响 B 的成功项目；
- A 重试成功后只清除 A 的错误并发布项目；
- 同一房间并发重试仍只触发一次存储读取。

### 页面契约测试

- 页面选择 `loadErrorsByRoomId[roomMesh.id]`；
- 错误分支位于 `FurnishWebView` 挂载之前；
- 分支包含“重试读取”和“返回房源库”；
- 重试调用现有 `loadProject(roomMesh)`；
- 重试期间按钮禁用。

### 回归验证

- Mobile 全套测试、TypeScript 和 Expo 公共配置；
- Android Debug 原生构建和 release JavaScript bundle；
- API 34 模拟器正常读取、软装进入、返回与再次进入；
- 全仓公开内容、Web、Rust 后端格式、Clippy 和测试；
- 推送公开 `main` 后等待 CI。

读取失败阻断行为以可控存储 Promise 和 Store 行为测试为主要证据；不伪造模拟器存储故障或真机结果。

## 完成标准

- 读取失败不会向页面发布可编辑空白项目；
- 用户能原位重试或安全返回；
- 重试成功恢复原有工作流；
- 多房间错误状态严格隔离；
- 正常空记录和损坏恢复语义不变；
- 所有自动化、构建和可用模拟器正常链路通过；
- 验证记录明确保留真机、生产签名和商店验收边界。
