# Roomark 软装按房间写队列设计

## 背景

`furnishStore` 当前用一个进程级 `furnishPersistenceQueue` 串行所有房间的 AsyncStorage 写入。串行化能防止同一房间的旧布局迟到覆盖新布局，但也让不同房间共享同一故障域：如果 A 房间的一次 `setItem` 永久 pending，B 房间之后的保存永远无法开始。

## 目标

- 保持同一房间写入严格串行。
- 不同房间的写入互不阻塞。
- 保持现有保存中、保存失败、重试、自动保存和退出前刷新行为。
- 不增加写超时，不改变存储键、项目 schema 或用户界面。

## 方案比较

1. **按房间维护 Promise 队列（采用）**：以 `roomId` 为键保存队列尾，同房间顺序不变，不同房间可并行。写入结算后只在仍是当前队列尾时删除 Map 项，避免删除后续已排队写入。
2. **给全局队列增加超时（拒绝）**：AsyncStorage 写入不可取消；超时后放行下一次写入会产生旧写入迟到覆盖新数据的风险。
3. **所有写入完全并行（拒绝）**：不同房间可用，但同一房间的完成顺序不可控，会破坏最后一次编辑获胜的语义。

## 数据流

`saveProject(project)` 继续先更新内存草稿和房间级 pending 计数，再调用 `enqueueFurnishPersistence(project.roomId, operation)`。队列函数读取该房间现有尾部 Promise，将新操作链接到尾部；没有尾部时立即开始。成功、失败和 pending 清理继续由现有 `saveProject` 分支处理。

## 故障语义

- A 房间写入永久 pending 时，A 的后续保存继续等待，避免乱序。
- B 房间没有共享尾部，因此可以开始并完成保存。
- 某次写入 reject 后，同房间下一次写入仍会执行，保持现有“失败不毒化队列”语义。
- 不尝试取消或超时写入。

## 验证

新增 Store 行为测试：启动 A 保存但不结算，随后启动 B 保存；两次底层写入都必须已开始，B 可先成功，而 A 仍保持 pending。现有同房间两次保存测试继续证明串行顺序和 pending 计数。

## 范围确认

该设计属于已确认的本地保存可靠性改进。依据用户已授权的自动 Looping 规则，Codex 自行确认本设计并继续实现，无需等待逐项回复。
